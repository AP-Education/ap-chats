# План від scaffold до переходу з Discord

## MVP простими словами

Команда може зайти своїм AP-акаунтом, знайти потрібний канал або людину, написати й прочитати повідомлення, побачити нове непрочитане та почати/прийняти дзвінок. Повідомлення не губляться при перезавантаженні чи переході між вебом і телефоном. Після пілоту основні розмови ведуться в Connect, Discord залишається тільки для погодженого архіву/тимчасового перехідного періоду.

Це і є «Slack-like»: зрозумілі канали, приватні розмови та швидкий дзвінок у контексті роботи, а не копіювання кожної функції Slack у першому релізі.

### Бойлерплейт перед фічами

Перший наступний PR: зафіксувати реальний Accounts client/redirects/audience, вибрати браузерний auth flow (BFF session/cookie чи SPA PKCE) після end-to-end spike, додати перевірку токена на API та auth provider у web. Мобільний login має використовувати system browser для OIDC, якщо embedded WebView не проходить вимоги провайдера/платформ. Не додаємо фальшивий login mode у production.

Другий PR: Postgres міграція для `workspace`, `member`, `conversation`, `conversation_member`, `message` і `outbox`; один наскрізний сценарій «створити канал → написати → прочитати після перезавантаження». Лише після нього вводимо Redis fan-out, чергу сповіщень і attachment storage. Prisma та contract-generation бібліотеку обираємо в цьому PR на підставі реальної схеми; порожній ORM-пакет зараз не потрібен.

Третій PR: realtime, reconnect і unread. Непрочитане обчислюється від збереженого cursor члена розмови, а не від кількості отриманих push. Події несуть стабільний ID для повторної доставки.

### Контрольні питання перед пілотом

- Чи один `sub` в Accounts однозначно ідентифікує людину між продуктами й організаціями? Що саме означає `appId` для Connect?
- Чи потрібна міграція історії Discord, чи достатньо залишити read-only архів? Це рішення змінює обсяг імпорту, але не модель нових чатів.
- Чи потрібні файли й threads у першому релізі для реального виходу з Discord? Визначити на пілоті до freeze MVP.
- Чи забезпечує обраний mobile call path системний UI та звук на заблокованому iPhone й Android? Звичайний push і WebView самі цього не гарантують.

Прогрес відстежувати по сценаріях користувача й показниках: успішний вхід, доставлення повідомлень після reconnect, unread між пристроями, час появи дзвінка на телефоні, відсоток невдалих викликів. Нові компоненти інфраструктури додавати, коли ці перевірки показують потребу.
