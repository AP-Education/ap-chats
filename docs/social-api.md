# Social API: ядро повідомлень

Усі HTTP-маршрути мають префікс `/api/workspaces/{workspaceId}/channels/{channelId}`. ID у шляху й тілі — UUID, `seq` та курсори — десяткові рядки, щоб не втрачати точність `bigint` у JavaScript. Запити потребують чинного токена Accounts та активного членства у workspace. Канал перевіряється знову всередині транзакції.

## Повідомлення та історія

| Метод і шлях                   | Тіло / query                                                  | Правило                                                                                                                         |
| ------------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `GET /messages/window`         | `messageId?`                                                  | Відкриває історію біля першого непрочитаного або цільового повідомлення; якщо непрочитаного немає, повертає найновішу сторінку. |
| `GET /messages`                | `before?`, `after?`, `snapshot?`, `limit?` (1–100, типово 40) | Публічний канал читає учасник workspace; приватний — лише учасник каналу. `before` та `after` не поєднуються.                   |
| `GET /messages/{messageId}`    | —                                                             | Повертає один item історії з актуальним станом повідомлення для realtime-оновлення.                                             |
| `POST /messages`               | `{markdown, clientNonce, replyToMessageId?, quoteText?}`      | Автор має бути учасником каналу. Повідомлення й entry створюються атомарно.                                                     |
| `PATCH /messages/{messageId}`  | `{markdown, revision?}`                                       | Лише автор. Невідповідна `revision` дає `409`.                                                                                  |
| `DELETE /messages/{messageId}` | —                                                             | Автор або менеджер каналу; лишається tombstone.                                                                                 |
| `POST /messages/batch-delete`  | `{messageIds: UUID[]}`                                        | 1–100 різних ID, одна транзакція; права перевіряються для всіх перед зміною.                                                    |

`GET /messages/window` і сторінки `GET /messages` повертають однакову форму `{items, snapshotSeq, firstUnreadSeq, unreadCount, hasOlder, olderCursor, hasNewer, newerCursor, readState}`. `items` відсортовані за зростанням `seq`; кожен item має `type: "MESSAGE"`, `message`, `author: {memberId, displayName, avatarPath}`, короткий контекст `reply` з автором, `forwardedFrom` і `pin`. Вікно непрочитаного містить до 12 попередніх повідомлень і до 40, починаючи з першого непрочитаного. Курсори ведуть до обох боків вікна. Для послідовних сторінок клієнт передає `snapshot`, щоб історія не зміщувалася через нові повідомлення; запит `after` без `snapshot` дочитує вже нові записи. Видалене повідомлення лишається у стрічці з `markdown: null`. Проєкція власного повідомлення повертає `clientNonce` для зіставлення з локальною спробою відправлення; для чужого він `null`.

На записі Markdown перевіряється, нормалізується й серіалізується назад; AST не зберігається. Згадка має синтаксис `:member[UUID]` і вказує на активного учасника каналу. Відповідь повертає канонічний Markdown та `contentVersion: 1`. Quote — знімок тексту з reply target у тому самому каналі; сервер порівнює виділений фрагмент із текстом джерела після уніфікації пробілів. Повтор `POST` із тим самим `clientNonce` і тим самим вмістом повертає створене повідомлення; інший вміст дає `409`.

## Pins, forwarding і read-state

| Метод і шлях               | Тіло                                                | Правило                                                                                                                     |
| -------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `GET /pins`                | —                                                   | Те саме право читання, що й для історії; повертає message ID, `seq`, автора, Markdown і дані закріплення.                   |
| `PUT /pins/{messageId}`    | —                                                   | Менеджер каналу; повторне закріплення ідемпотентне.                                                                         |
| `DELETE /pins/{messageId}` | —                                                   | Менеджер каналу; повторне зняття ідемпотентне.                                                                              |
| `POST /messages/forward`   | `{sourceChannelId, batchNonce, messageIds: UUID[]}` | 1–100 повідомлень у порядку масиву. Джерело має бути доступне для читання, цільовий канал — для запису. Уся пачка атомарна. |
| `GET /read-state`          | —                                                   | Повертає `lastReadEntrySeq` і точний `unreadCount`; для читача публічного каналу без участі повертає `null`.                |
| `PUT /read-state`          | `{seq: "123"}`                                      | Лише учасник каналу. Курсор не рухається назад і не перевищує поточний `lastEntrySeq`.                                      |

Менеджер приватного каналу — його учасник; публічного — творець або власник workspace. Forward створює нові повідомлення й позиції та копіює канонічний Markdown. Історія повертає проєкцію автора джерела, але не відкриває ID вихідного повідомлення без окремої перевірки доступу. Повтор із тим самим `batchNonce` повертає вже створену пачку; інший набір із тим самим nonce дає `409`. Згадки у forward залишаються текстом знімка і не створюють нових mention-сповіщень.

## Реакції

| Метод і шлях                                    | Тіло      | Правило                                                                                                                                              |
| ----------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /messages/{messageId}/reactions?emoji=`    | —         | Те саме право читання, що й для історії; до 100 реакцій, новіші першими: `{memberId, displayName, avatarPath, emoji}`. Без `emoji` усі емодзі разом. |
| `POST /messages/{messageId}/reactions`          | `{emoji}` | Учасник каналу; повтор ідемпотентний. Повертає `{emoji, count, recentMemberIds, reacted: true}`.                                                     |
| `DELETE /messages/{messageId}/reactions?emoji=` | —         | Знімає лише власну реакцію; повтор ідемпотентний. Повертає `{emoji, count, recentMemberIds, reacted: false}`.                                        |

`emoji` перевіряє DTO: один повністю кваліфікований емодзі з набору Unicode RGI (`\p{RGI_Emoji}`), тож кожна реакція має одне написання; інше значення дає `400`. Повідомлення тримає до 20 різних емодзі: нова двадцять перша дає `409`, а вже наявні приймаються далі. Видалене повідомлення реакцій не приймає. Обмежень довжини в схемі немає: власні емодзі workspace, коли з'являться, стануть окремим посиланням на свою таблицю, а не довшим рядком.

`message_reactions(message_id, emoji, member_id)` — первинний ключ і водночас індекс для обох читань. View `message_reaction_summaries` визначає зведення одного емодзі один раз: `count`, до трьох останніх людей і час першої реакції; її читають і сторінка історії, і відповідь на зміну реакції. Сторінка історії підтягує згадки та реакції `LEFT JOIN LATERAL` з `json_agg`: звичайний join повторив би рядок для кожної реакції й зламав ліміт сторінки. Кожен item історії несе `reactions: [{emoji, count, recentMemberIds, reacted}]` у порядку першої появи емодзі; `reacted` — чи є серед них читач. Повний список людей у проєкцію не входить і завантажується на вимогу. Лічильник не денормалізується: агрегат за індексом дешевший за ще одну гарячу точку запису. Реакції не рухають `seq`, не впливають на unread і не надсилають сповіщень.

## Профіль людини

`PUT /api/user-profile/me` приймає `{idToken}` разом із чинним API access token. Сервер перевіряє підпис ID token через наявний OIDC verifier, відповідність `sub` та `appId`, після чого оновлює лише профіль цього користувача. Клієнт викликає його один раз після входу з новим ID token; читання повідомлень не запускає синхронізацію. `user_profiles` зберігає локальну проєкцію імені й аватара, `workspace_members` посилається на неї, а сервер при читанні історії й pins робить join. Історичні профілі, створені міграцією лише з `userId`, матимуть `displayName: null`, доки їхній власник не відкриє застосунок із чинним ID token.

`readState` у сторінці історії дорівнює `null` для читача публічного каналу, який не вступив до нього. `unreadCount` рахує нові записи інших авторів, включно з дзвінками, крім видалених повідомлень, у межах `snapshotSeq`. Сервер перевіряє, що підтверджений `seq` існує й не перевищує поточну верхню позицію; він не зберігає доказу показу сторінки конкретному клієнту.

`GET /api/workspaces/{workspaceId}/read-state` повертає зведення `{channelId, kind, lastReadEntrySeq, unreadCount}[]` для всіх каналів участі одним запитом. Воно живить бейджі каналів і особистих розмов. `kind` дає змогу рахувати ці два бейджі окремо.

`GET` і `PATCH /api/workspaces/{workspaceId}/channels/{channelId}/notifications` читають та змінюють особисті налаштування каналу. `PATCH` приймає `{type: "level", level: "default" | "all" | "mentions" | "none"}`, `{type: "mute", duration: "hour" | "day" | "indefinite"}` або `{type: "unmute"}`. Mute приглушує сигнал, але не змінює кількість непрочитаних.

## Realtime

У просторі Socket.IO `/chats` клієнт після `session:ready` надсилає `social:watch` з `{workspaceId, channelId}`. Підписка доступна лише поточному учаснику каналу; `social:unwatch` залишає кімнату. Події `social:changed` несуть тип (`social.message.created`, `social.message.updated`, `social.message.deleted`, `social.messages.batch-deleted`, `social.forward.batch-created`, `social.pin.added`, `social.pin.removed`) та ID каналу. Одиночні події містять `messageId`; пакетне видалення й forward містять `messageIds`, а forward також `firstSeq` і `lastSeq`. Клієнт сам вирішує, чи оновлювати REST-дані. Реакції приходять окремою подією `social:reaction` з `{workspaceId, channelId, messageId, actorMemberId, added, reaction}`: це вже новий стан чипа, який клієнт застосовує на місці, а не привід перечитати повідомлення. Перед відправкою gateway повторно перевіряє членство поточних sockets кімнати й видаляє з неї тих, хто втратив доступ. Локальні події після commit мають режим best effort; після reconnect клієнт запитує `GET /messages?after={lastSeq}` та оновлює видимі записи.

Після створення або видалення запису `social:unread` надходить у персональну кімнату кожного поточного учасника каналу. Подія несе `eventId`, канал, тип розмови, операцію, позиції записів та індивідуальне рішення `alert`; клієнт змінює лише відповідний лічильник. `social:read-state` надсилає авторитетні курсор і лічильник усім пристроям учасника після `PUT /read-state`. Snapshot workspace запитується при відкритті, поверненні до вкладки та reconnect для відновлення після пропущених socket-подій. Сокет-підписка `social:watch` залишається лише для видимої історії каналу.
