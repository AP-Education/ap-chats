# Social API: ядро повідомлень

Усі HTTP-маршрути мають префікс `/api/workspaces/{workspaceId}/channels/{channelId}`. ID у шляху й тілі — UUID, `seq` та курсори — десяткові рядки, щоб не втрачати точність `bigint` у JavaScript. Запити потребують чинного токена Accounts та активного членства у workspace. Канал перевіряється знову всередині транзакції.

## Повідомлення та історія

| Метод і шлях                   | Тіло / query                                             | Правило                                                                                                       |
| ------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `GET /messages`                | `before?`, `after?`, `limit?` (1–100, типово 40)         | Публічний канал читає учасник workspace; приватний — лише учасник каналу. `before` та `after` не поєднуються. |
| `POST /messages`               | `{markdown, clientNonce, replyToMessageId?, quoteText?}` | Автор має бути учасником каналу. Повідомлення й entry створюються атомарно.                                   |
| `PATCH /messages/{messageId}`  | `{markdown, revision?}`                                  | Лише автор. Невідповідна `revision` дає `409`.                                                                |
| `DELETE /messages/{messageId}` | —                                                        | Автор або менеджер каналу; лишається tombstone.                                                               |
| `POST /messages/batch-delete`  | `{messageIds: UUID[]}`                                   | 1–100 різних ID, одна транзакція; права перевіряються для всіх перед зміною.                                  |

`GET /messages` повертає `{items, snapshotSeq, hasMore, nextCursor, readState}`. `readState` тут містить лише `lastReadEntrySeq`, щоб гортання не рахувало всі непрочитані записи. `items` відсортовані за зростанням `seq`; зараз кожен item має `type: "MESSAGE"`, `message` і `pin`. `before` читає старіші записи, `after` — новіші для відновлення після reconnect. `nextCursor` — найстаріший `seq` для `before`, найновіший для `after`. `snapshotSeq` фіксує верхню позицію сторінки. Видалене повідомлення лишається у стрічці з `markdown: null`.

На записі Markdown перевіряється, нормалізується й серіалізується назад; AST не зберігається. Згадка має синтаксис `:member[UUID]` і вказує на активного учасника каналу. Відповідь повертає канонічний Markdown та `contentVersion: 1`. Quote — знімок тексту з reply target у тому самому каналі. Повтор `POST` із тим самим `clientNonce` і тим самим вмістом повертає створене повідомлення; інший вміст дає `409`.

## Pins, forwarding і read-state

| Метод і шлях               | Тіло                                                | Правило                                                                                                                     |
| -------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `GET /pins`                | —                                                   | Те саме право читання, що й для історії.                                                                                    |
| `PUT /pins/{messageId}`    | —                                                   | Менеджер каналу; повторне закріплення ідемпотентне.                                                                         |
| `DELETE /pins/{messageId}` | —                                                   | Менеджер каналу; повторне зняття ідемпотентне.                                                                              |
| `POST /messages/forward`   | `{sourceChannelId, batchNonce, messageIds: UUID[]}` | 1–100 повідомлень у порядку масиву. Джерело має бути доступне для читання, цільовий канал — для запису. Уся пачка атомарна. |
| `GET /read-state`          | —                                                   | Повертає `lastReadEntrySeq` і точний `unreadCount`; для читача публічного каналу без участі повертає `null`.                |
| `PUT /read-state`          | `{seq: "123"}`                                      | Лише учасник каналу. Курсор не рухається назад і не перевищує поточний `lastEntrySeq`.                                      |

Менеджер приватного каналу — його учасник; публічного — творець або власник workspace. Forward створює нові повідомлення й позиції та копіює канонічний Markdown. API показує ID автора джерела, але не відкриває ID вихідного повідомлення без окремої перевірки доступу. Повтор із тим самим `batchNonce` повертає вже створену пачку; інший набір із тим самим nonce дає `409`. Згадки у forward залишаються текстом знімка і не створюють нових mention-сповіщень.

`readState` у сторінці історії дорівнює `null` для читача публічного каналу, який не вступив до нього. `unreadCount` у `GET/PUT /read-state` рахує нові повідомлення інших авторів, крім tombstone; його точний підрахунок залежить від кількості непрочитаних записів і не запускається при кожному гортанні історії. Сервер перевіряє, що підтверджений `seq` існує й не перевищує поточну верхню позицію; він не зберігає доказу показу сторінки конкретному клієнту.

## Realtime

У просторі Socket.IO `/chats` клієнт після `session:ready` надсилає `social:watch` з `{workspaceId, channelId}`. Підписка доступна лише поточному учаснику каналу; `social:unwatch` залишає кімнату. Події `social:changed` несуть тип (`social.message.created`, `social.message.updated`, `social.message.deleted`, `social.messages.batch-deleted`, `social.forward.batch-created`, `social.pin.added`, `social.pin.removed`) та ID каналу. Одиночні події містять `messageId`; пакетне видалення й forward містять `messageIds`, а forward також `firstSeq` і `lastSeq`. Клієнт сам вирішує, чи оновлювати REST-дані. Перед відправкою gateway повторно перевіряє членство поточних sockets кімнати й видаляє з неї тих, хто втратив доступ. Локальні події після commit мають режим best effort; після reconnect клієнт запитує `GET /messages?after={lastSeq}` та оновлює видимі записи.
