# 0008. Оновлення застосунків без ревʼю в сторах

Мобільний застосунок (`mobile/`) — Expo-оболонка над remote web (`EXPO_PUBLIC_WEB_URL`). Майже весь UI чатів живе у `web/` і доходить до людей одразу після деплою. Через App Store і Google Play зараз проходить лише власний код оболонки: таби, дзвінки, push, composer, bridge. Кожен фікс у ньому чекає на ревʼю. Згодом з'явиться десктопна оболонка на Electron з тими самими задачами.

Рішення:

- **Мобільна оболонка.** `expo-updates` за відкритим протоколом Expo Updates. Маніфести віддає модуль `updates` у цьому API, а бандли лежать у DO Spaces.
- **Десктопна оболонка.** `electron-updater` з вбудованим провайдером DigitalOcean Spaces, без власного API.
- **Сумісність web і обох оболонок.** Capability-токени для функцій і мінімальний номер нативної збірки для примусового оновлення.

## Шари оновлення

| Шар          | Що містить                                                     | Канал доставки              |
| ------------ | -------------------------------------------------------------- | --------------------------- |
| Web          | `web/`, весь UI чатів                                          | деплой сервера, одразу всім |
| JS оболонки  | RN-код `mobile/src`                                            | OTA через `expo-updates`    |
| Нативний код | модулі, config plugins, entitlements, SDK; уся збірка Electron | стор або новий інсталятор   |

OTA ніколи не змінює нативний шар. Нові нативні можливості (LiveKit, CallKit, WebRTC тощо) і далі йдуть через ревʼю.

### Правила сторів

- **Apple.** App Review Guidelines 2.5.2 забороняють завантажувати код, що змінює функціональність застосунку. Виняток для інтерпретованого коду дає Apple Developer Program License Agreement §3.3.1(B). Такий код не може змінювати основне призначення застосунку, створювати магазин чи платформу для іншого коду або обходити підпис, sandbox і захист ОС.
- **Google Play.** Політика Device and Network Abuse забороняє завантажувати виконуваний код з-поза Google Play. Виняток — код, що виконується у віртуальній машині чи інтерпретаторі з непрямим доступом до Android API.

Відсутність змін у нативному коді не робить будь-яку OTA-зміну допустимою. Кожна OTA-фіча має пройти ревʼю, якби подавалась у стор, і не змінювати призначення застосунку. Нова суттєва функціональність, а також усе, що стосується платежів, підписок чи збору даних, іде через стор, навіть якщо технічно поміщається в JS.

## Чому власний сервер для Expo, а не EAS Update

EAS Update тарифікується за MAU, і безкоштовний план має ліміт. Вимога — нульова вартість ліцензій незалежно від кількості користувачів. Адреса сервера оновлень вшивається в бінарник, тому вибір треба зробити до першого релізу з `expo-updates`. Пізніший переїзд з EAS коштуватиме ще одного релізу через стор. EAS Build і `eas submit` лишаються.

Electron на цей вибір не впливає. `electron-updater` публікує артефакти й `latest*.yml` прямо в Spaces і сам підтримує поступовий rollout через `stagingPercentage`.

**Ціна власного сервера:**

- реалізація й підтримка протоколу Expo Updates та code signing, а також сумісність з новими версіями `expo-updates` при кожному оновленні Expo SDK;
- діагностика, яку EAS дає з коробки: які пристрої на якому update, помилки за updateId. Її треба побудувати самим (див. «Rollout»);
- відновлення після збоїв: недоступний API чи Spaces не має ламати запуск. Клієнт тоді працює на останньому завантаженому або вбудованому бандлі;
- трафік Spaces. JS-бандл оболонки важить кілька мегабайтів, тож це незначно.

Для порівняння з EAS потрібні фактичні MAU (активні пристрої з таблиці push-токенів) і частота OTA-релізів. Якщо MAU стабільно вкладається в безкоштовний ліміт EAS, а підтримка сервера забирає більше часу, ніж очікується, рішення варто переглянути до першого стор-релізу з `expo-updates`.

## Сумісність web і оболонки

### Capability-токени

Оболонка вже додає до User-Agent токени `ApAppMobile/1 ApAppTabBar/1` (`mobile/src/features/webview/utils/shell-user-agent.ts`, дзеркало у shell-sdk ap-app). Web визначає оболонку синхронно, без гонки з bridge. Рішення розширює цей механізм:

- Кожна нативна можливість, від якої залежить web, отримує власний токен `ApApp<Capability>/<n>`. Номер змінюється лише при несумісній зміні протоколу.
- Web вмикає функцію за наявністю токена й має fallback для старих оболонок.
- Десктопна оболонка оголошує `ApAppDesktop/1` і власний набір токенів.
- OTA додає токен, лише якщо потрібний нативний код уже є в бінарнику. Токен, що вимагає нового нативного модуля, з'являється тільки з новим бінарником.

### Примусове оновлення

Fingerprint (`runtimeVersion`) — це хеш нативного шару. Він показує, чи підходить OTA-бандл до бінарника, але не дає визначити, яка збірка старіша. Тому примусове оновлення спирається на номер нативної збірки:

- iOS `buildNumber` і Android `versionCode` уже монотонно зростають (`appVersionSource: remote`, `autoIncrement` в `eas.json`). Для Electron таку саму роль виконує semver.
- `GET /api/updates/compat?platform=` повертає `minSupportedBuild`.
- Якщо збірка оболонки менша, оболонка показує екран «Онови застосунок» з посиланням у стор або на інсталятор.
- Це аварійний важіль на випадок, коли web більше не може підтримувати старий bridge. Для звичайних функцій використовуються токени.

Збій `/compat` не блокує застосунок (fail open):

- запит має короткий таймаут;
- при помилці оболонка бере останню успішну відповідь з локального сховища;
- якщо збереженої відповіді немає, оболонка працює далі.

Блокує запуск лише явна відповідь сервера, що збірка не підтримується.

## Модуль `updates` (мобільна оболонка)

Модуль `src/components/updates`, три таблиці (Drizzle, міграція `0038_app_updates`):

```
app_runtimes             — нативні збірки в сторах
  (platform, runtime_version) pk, build_number, created_at

app_updates              — що пропонується оболонкам
  id (uuid — це updateId протоколу),
  kind (update | rollback_to_embedded),
  platform (ios | android), channel (production | preview),
  runtime_version → app_runtimes,
  manifest (jsonb: launch asset, assets з hash і url; null для rollback_to_embedded),
  rollout_percent (0–100), status (active | paused | revoked),
  mandatory, source_update_id (оригінал при republish),
  git_commit, notes, created_by, created_at

app_update_launch_stats  — запуски за день
  (platform, runtime_version, update_id, day) unique nulls not distinct,
  launches, successes, emergency_launches
```

`rollBackToEmbedded` — звичайний запис з `kind = rollback_to_embedded`. Він бере участь у rollout і виборі так само, як бандл. Update не можна створити для runtime, якого немає в `app_runtimes`: таке оновлення не запуститься на жодному бінарнику.

Публічні ендпоінти (оновлення має дійти й до пристрою без сесії):

- `GET /api/updates/expo/manifest` — протокол Expo Updates.
  - Сервер читає заголовки `expo-protocol-version` (лише `1`), `expo-platform`, `expo-runtime-version`, `expo-channel-name` та ідентифікатор установки.
  - У multipart-відповіді повертає одне з трьох: маніфест найновішого `active` update для цього runtime, директиву `noUpdateAvailable` або директиву `rollBackToEmbedded`. Невідомий канал отримує `noUpdateAvailable`.
  - Якщо клієнт надсилає `expo-expect-signature`, маніфест і директива підписуються ключем `EXPO_UPDATES_PRIVATE_KEY`. Клієнт перевіряє підпис через `codeSigningCertificate`. Без налаштованого ключа сервер відповідає 503, а не непідписаною відповіддю.
- `GET /api/updates/compat` — див. «Примусове оновлення». Значення беруться з env (`UPDATES_MIN_BUILD_*`, `UPDATES_STORE_URL_*`).
- `POST /api/updates/launches` — телеметрія запуску (див. «Rollout і критерії успіху»). Звіти для runtime або update, яких немає в базі, відкидаються.

Адмін-ендпоінти `/api/updates/admin/*` доступні лише з токеном `UPDATES_ADMIN_TOKEN`, який зберігається тільки в секретах CI. Без налаштованого токена адмін-API вимкнений.

| Ендпоінт                          | Дія                                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `POST runtimes`                   | зареєструвати fingerprint і номер збірки після релізу в стор                                            |
| `POST releases`                   | опублікувати update. Production стартує з 10 %, preview — зі 100 %. 409, якщо runtime не зареєстрований |
| `GET releases?channel=&platform=` | список з сумарними запусками                                                                            |
| `PATCH releases/:id/rollout`      | змінити відсоток. Відновлює `paused`                                                                    |
| `POST releases/:id/pause`         | `paused`                                                                                                |
| `POST releases/:id/rollback`      | у транзакції: republish або `rollback_to_embedded`, проблемний — `revoked`                              |

Бандли й ассети лежать у Spaces за незмінними URL з hash в імені та віддаються через CDN, а не через API.

Rollout детермінований: сервер бере перші 4 байти sha256 від `installationId:updateId` за модулем 100 і порівнює з `rollout_percent`. Тоді один пристрій не перемикається між версіями від запиту до запиту, а кожен update отримує власну вибірку пристроїв. Пристрій поза rollout отримує попередній `active` update. Цей update не новіший за той, що вже стоїть на пристрої, тож клієнт нічого не змінює. Пристрій без ідентифікатора отримує лише update на 100 %.

## Відкат

Клієнт `expo-updates` запускає найновіший сумісний update, який має. Якщо почати віддавати старіший маніфест, пристрої, що вже оновились, лишаться на проблемному update. Тому відкат для кожного клієнта описаний окремо.

**Expo:**

- Проблемний update отримує статус `paused`: нові пристрої його більше не отримують.
- **Відкат на попередній OTA.** Вміст попереднього update перепублікується як новий update з новим `id` і `created_at`. `source_update_id` вказує на оригінал. Ассети ті самі, нового `expo export` не треба. Оновлені пристрої сприймають його як новіший і переходять на нього.
- **Відкат до вбудованого бандла.** Застосовується, якщо попереднього OTA немає або він теж зламаний. Сервер віддає директиву `rollBackToEmbedded`, і клієнт повертається до бандла з бінарника.
- Проблемний update переходить у `revoked` і більше ніколи не віддається.

**Electron:**

- `electron-updater` не робить даунгрейд за замовчуванням. Стандартний шлях — випустити виправлену збірку з вищою версією.
- До виходу виправлення поширення зупиняється: `stagingPercentage: 0` у `latest*.yml`.

**Web:** повторний деплой попередньої версії, як зараз.

## Мобільний клієнт

- `expo-updates`, `updates.url` вказує на `/api/updates/expo/manifest`, `runtimeVersion: { policy: 'fingerprint' }`. Маніфести підписані; сертифікат `mobile/certs/updates-certificate.pem` вбудований у збірку, приватний ключ є лише на сервері.
- Канал задає змінна `APP_UPDATES_CHANNEL` у профілі `eas.json` (`production`, `preview`; `apk` — `preview`). `app.config.ts` кладе її в заголовок `expo-channel-name`. Поле `channel` з `eas.json` не використовується: воно налаштовує EAS Update. Збірка без адреси API, як-от локальна, оновлень не бере; збірка без каналу питає, але сервер їй нічого не пропонує.
- Ідентифікатор установки для rollout сервер бере із заголовка `eas-client-id`, який надсилає `expo-updates`, або з `ap-installation-id`, якщо оболонка задає його сама. Який з них реально приходить від SDK 57, перевіряється на release-збірці перед першим релізом.
- Оновлення перевіряється на старті й при поверненні у foreground, не частіше ніж раз на 15 хвилин (`checkAutomatically: 'NEVER'`, перевіркою керує оболонка). Завантаження йде у фоні, застосування — на наступному холодному старті.
- **Mandatory і відкат.** Mandatory update і директива `rollBackToEmbedded` застосовуються раніше, через `reloadAsync`, але лише коли перезапуск нічого не знищить. Він чекає, поки:
  - триває або дзвонить дзвінок;
  - іде вхід чи вихід (браузерний OIDC-флоу);
  - сторінка повідомляє про роботу, яку втратить перезапуск: відправку повідомлення, завантаження файлів, запис голосового.

  Сторінка сама надсилає `{ type: 'updates/busy', source, busy }` при кожній зміні, і один раз `busy: false`, коли джерело зʼявляється. Так оболонка знає, що сторінка вміє звітувати. Це робиться лише під оболонкою з токеном `ApAppReloadGuard/1`. Сторінку, яка не звітує (старий web), оболонка перезапускає лише у background. Текст composer і невідправлені повідомлення зберігаються в `localStorage`, тож перезапуск їх не втрачає.

  Запит від оболонки з відповіддю web і таймаутом відкинуто: звіти від сторінки обходяться без таймаутів, а кілька джерел (і кілька застосунків у host) звітують незалежно.

- **Звіт про запуск.** Один на холодний старт, лише якщо застосунок стартував у foreground (дзвінок, що будить застосунок у фоні, сторінки не показує). Запуск успішний, якщо бандл протримався 10 секунд і сторінка стартувала (`page/started`) протягом 30 секунд; без WebView, як на екрані входу, достатньо 10 секунд. `updateId` — null для вбудованого бандла.

- Перший реліз з `expo-updates` іде через стор. Після нього JS оболонки оновлюється OTA.

## Десктоп (Electron)

- Оболонка над тим самим remote web, тож UI оновлюється деплоєм web.
- Сама збірка (main, preload, Electron) оновлюється через `electron-updater` з провайдером Spaces, диференційно за blockmap.
- Розповсюдження пряме, без Mac App Store.
- macOS-збірки підписані й нотаризовані.
- Windows-збірки підписані. Сертифікат платний; без нього застосунок працює, але SmartScreen показує попередження.
- Capability-токени й `/compat` працюють так само, як у мобільній оболонці.

## Rollout і критерії успіху

**Телеметрія.** Оболонка після запуску надсилає в API:

- платформу, `runtimeVersion` і `updateId` (null для бандла з бінарника);
- `isEmergencyLaunch` з `expo-updates`: `true`, якщо клієнт відкотився через падіння нового бандла;
- чи стартувала оболонка й завантажила web (див. «Звіт про запуск» вище).

Помилки JS оболонки тегуються `updateId`. З цих даних модуль `updates` рахує по кожному update частку успішних запусків і частку emergency launch.

**Етапи:** 10 % → 50 % → 100 %, з паузою щонайменше 24 години між етапами.

Етап розширюється лише за таких умов:

- успішних запусків не менше, ніж у попередньому update;
- emergency launch немає;
- нових типів помилок оболонки немає.

Інакше update переходить у `paused`, і починається відкат.

**Відповідальний.** Розширення й відкат виконує черговий за релізом. Він вказується в описі CI-джоба. Автоматичного розширення немає.

**Перевірка відкату.** Перед першим production OTA кожен сценарій відкату проходить на реальному release-білді (TestFlight / internal testing) через канал `preview`:

- republish попереднього update;
- `rollBackToEmbedded`;
- `paused` під час rollout.

## Публікація

CI-джоб `publish-update`:

1. `eas env:pull` для EAS-оточення з назвою каналу: бандл несе ті самі `EXPO_PUBLIC_*`, що й збірки цього каналу.
2. Обчислення fingerprint (`expo-updates runtimeversion:resolve`) з тим самим `APP_UPDATES_CHANNEL`.
3. `expo export --platform ios|android` у `mobile/`.
4. Завантаження бандла й ассетів у Spaces під `app-updates/<sha256><розширення>`, публічно, з `Cache-Control: immutable`. Файл, який уже є в бакеті, не надсилається повторно.
5. `POST /api/updates/admin/releases`. Якщо збірки з таким fingerprint немає в `app_runtimes`, API відповідає 409 і публікація зупиняється.

Після кожного релізу в стор CI-джоб `register-runtime` записує fingerprint і номер збірки в `app_runtimes`. Fingerprint береться з EAS (`eas build:list`), тобто той, з яким збірку справді зроблено. Розширення rollout, пауза й відкат — окремі ручні CI-джоби. Скрипти лежать у `scripts/updates/`, workflows — у `.github/workflows/`.

**Fingerprint.** `mobile/fingerprint.config.js` виключає версії й номери збірок, `.gitignore` і `eas.json`: вони не змінюють нативний код, а інакше кожна збірка мала б свій runtime і правка `eas.json` відрізала б збірки в сторах від оновлень. Конфіг застосунку, зокрема адреса API й канал, у fingerprint входить.

**Налаштування GitHub.**

| Що                                                 | Де       | Значення                                                             |
| -------------------------------------------------- | -------- | -------------------------------------------------------------------- |
| `UPDATES_ADMIN_TOKEN`                              | secret   | той самий, що в Ansible Vault                                        |
| `UPDATES_SPACES_KEY`, `UPDATES_SPACES_SECRET`      | secret   | ключ Spaces з правом запису в бакет оновлень                         |
| `EXPO_TOKEN`                                       | secret   | токен робота Expo (безкоштовний): `env:pull` і `build:list`          |
| `UPDATES_API_URL`                                  | variable | адреса API без `/api`                                                |
| `UPDATES_SPACES_ENDPOINT`, `UPDATES_SPACES_BUCKET` | variable | напр. `fra1.digitaloceanspaces.com` і назва бакета                   |
| `UPDATES_ASSETS_URL`                               | variable | публічна адреса бакета (або CDN), з якої телефони завантажують файли |

**Ключ підпису маніфестів.** Сервер підписує маніфести під час відповіді, тому приватний ключ зберігається лише в секретах сервера. CI його не має: публікацію обмежує `UPDATES_ADMIN_TOKEN`. Сертифікат вшивається в бінарник. Ротація ключа потребує нового бінарника, тому сертифікат одразу випускається з довгим строком дії.

**Канали.** Кожен профіль `eas.json` задає `APP_UPDATES_CHANNEL`, що збігається з його EAS-оточенням: `preview` — `preview`, `production` і `apk` — `production`. Збірка отримує OTA лише зі свого каналу. Профіль `development` канал не має: dev client працює з Metro, а не з OTA.

## Як публікувати OTA

Усі дії — GitHub Actions з ручним запуском (`workflow_dispatch`): через вкладку Actions або через `gh`. Локальної публікації немає, бо адмін-токен є лише в CI. Кожна дія лишає запис: хто, коли й з якого коміту.

**Звичайний цикл:**

1. Зміна стосується лише JS у `mobile/src` і злита в `main`. Нові нативні модулі, config plugins чи зміни в `app.json` означають нову збірку в стор.
2. Публікація в `preview`:
   ```bash
   gh workflow run publish-update -f channel=preview -f platform=all -f notes="fix: call screen freeze"
   ```
   Якщо fingerprint не збігається з жодною збіркою в сторі, джоб падає. У summary джоба є `updateId`. Публікація в `production` іде через GitHub environment `production`, де можна вимагати підтвердження.
3. Перевірка на preview-збірці (TestFlight / internal testing): закрити й відкрити застосунок двічі. Перший запуск завантажує update, другий його застосовує.
4. Публікація в `production` з того самого коміту. Стартовий rollout — 10 %:
   ```bash
   gh workflow run publish-update -f channel=production -f platform=all -f notes="fix: call screen freeze"
   ```
5. Розширення за критеріями з «Rollout і критерії успіху»:
   ```bash
   gh workflow run update-status   -f channel=production
   gh workflow run update-rollout  -f update=<updateId> -f percent=50
   gh workflow run update-rollout  -f update=<updateId> -f percent=100
   ```

`update-status` виводить у summary джоба всі update каналу:

- статус і rollout;
- кількість запусків, частку успішних запусків і emergency launch;
- коміт і автора.

**Обовʼязкове оновлення** — `-f mandatory=true` у `publish-update`. Перезапуск відкладається за правилами з «Мобільний клієнт». Використовується лише для виправлень, без яких оболонка не працює.

**Після релізу в стор:**

```bash
gh workflow run register-runtime -f platform=ios -f build=12
```

**Інцидент:**

```bash
gh workflow run update-pause    -f update=<updateId>                  # зупинити поширення
gh workflow run update-rollback -f update=<updateId>                  # republish попереднього update
gh workflow run update-rollback -f update=<updateId> -f embedded=true # повернути до бандла зі стору
```

`update-rollback` переводить проблемний update у `revoked`. Republish публікується одразу на 100 % того самого каналу.

**Вартість.** Публікація — це `expo export` на Linux-раннері, кілька хвилин. macOS-раннер не потрібен. Джоби вкладаються в безкоштовні хвилини GitHub Actions організації.

## Порядок впровадження

1. Capability-токени для наявних нативних можливостей і `/api/updates/compat` з fail-open логікою в оболонці.
2. Модуль `updates`: таблиця, маніфест Expo, підпис, rollout, відкат, телеметрія запуску.
3. `expo-updates` у `mobile/` з каналом у профілях `eas.json`, перевірка сценаріїв відкату на release-білді, реліз через стор.
4. CI-джоби `publish-update`, `update-status`, `update-rollout`, `update-pause`, `update-rollback`, `register-runtime`.
5. Electron з провайдером Spaces — разом з появою десктопної оболонки.

## Відкриті питання

- Де розміщується Electron-оболонка: у цьому репозиторії поряд з `mobile/` чи разом з host-застосунком ap-app?
- Фактичні MAU і частота OTA-релізів для перевірки рішення проти безкоштовного ліміту EAS.
