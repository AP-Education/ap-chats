# Пошук людей і чатів

Пошук у панелі Chats відкриває спільний каталог поточної компанії. Він знаходить доступні канали, власні особисті розмови й активних колег за назвою або іменем. Наявність результату не залежить від завантажених сторінок списку DM. Вибір колеги використовує чинне ідемпотентне відкриття direct-messages.

На телефоні пошук займає весь екран і враховує відступ системної клавіатури. Стрілки змінюють вибір, Enter відкриває результат, Escape або Back закриває вікно. Закриття під час відкриття DM скасовує очікування відповіді та запобігає пізньому переходу.

## API

`GET /api/workspaces/:workspaceId/search?q=...` вимагає авторизації та активної участі у workspace. Відповідь має групи `channels`, `conversations`, `people`. Кожна містить не більше 20 результатів. Запит обмежено 80 символами; порожній запит повертає порожні групи. Шаблони `%`, `_` і `\` шукаються буквально. Точний збіг і початок імені мають пріоритет, після них порядок визначають імʼя та id.

Канали проходять перевірку участі ADR 0001 у SQL. DM додатково перевіряють пару співрозмовників. Колега з доступним DM у цьому workspace не дублюється в групі людей. Власний історичний DM із колегою, який залишив компанію, показує відповідну позначку. Пошук не повертає чужі DM, приховані від користувача канали, ботів або людей з інших компаній.

[ADR 0004](adr/0004-workspace-conversation-search.md) визначає межі, власність і поведінку кешу. Пошук по тексту повідомлень потребує окремого рішення.

## Автоматичні перевірки

```sh
node --import tsx --import ./src/testing/test-env.ts --test src/components/social/conversation-search/*.spec.ts
pnpm test:web
pnpm --filter @ap-chats/web exec playwright install --with-deps chromium webkit
pnpm --filter @ap-chats/web test:search
```

PostgreSQL/PGlite перевіряє видимість, ролі та відкликання доступу, ізоляцію workspace, власні/чужі DM, видалених учасників, Unicode, буквальні спеціальні символи, сортування й ліміти. Браузерна suite використовує production-компоненти пошуку та операцію відкриття DM, локальну fixture API й синтетичні дані. Chromium перевіряється на desktop, 390 px та 320 px із 4x CPU; WebKit — на телефонному viewport без CPU throttling.

Браузерні сценарії покривають групи результатів, клавіатуру, Back/Escape, очищення, помилки й retry, швидку зміну запиту, закриття під час POST, зміну акаунта/workspace, realtime відкликання доступу та клавіатурні відступи.

Реальний compiled API перевіряється окремо з Nest guards/validation, PostgreSQL та Valkey. Використовуються лише окремі тестові контейнери й синтетичні облікові дані; приватні dotenv-файли пропускаються. Порти 5438 і 6388 мають бути вільними:

```sh
docker compose --env-file /dev/null -f infra/docker-compose.search-test.yml up -d --wait
pnpm build
node --import tsx test/search.integration.mts
docker compose --env-file /dev/null -f infra/docker-compose.search-test.yml down
```

Цей сценарій перевіряє авторизацію, query DTO, приховування назв, одночасне відкриття того самого DM та негайне відкликання доступу. Обидва набори підключено до CI.

## Перевірка вигляду та мобільних WebView

Після `test:search` можна запустити `pnpm --filter @ap-chats/web exec vite preview --config tests/search/vite.config.mts` і відкрити `http://127.0.0.1:5570/`. Параметр `?dark=1` показує темну тему. Це локальний тестовий екран із синтетичними людьми й каналами.

Джерела та команди [Android/iOS перевірок](../test/search-native/README.md) збережені в репозиторії. Вони запускають реальні компоненти пошуку в системних WebView, перевіряють нативне введення та переходи. Авторизація повного Expo AP App та його інші можливості цими фокусованими сценаріями не перевіряються.
