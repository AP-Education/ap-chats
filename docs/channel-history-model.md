# Рішення: історія каналу через індекс позицій і окремі моделі

**Статус:** погоджена модель і реалізоване backend-ядро, 26 вересня 2026 року. Цей запис замінює схему `messages.seq` і правила тредів із розділу 3 [початкового проєкту](chat-domain-design.md); фактичні маршрути наведено в [Social API](social-api.md), канали й членство — в [Communities API](communities-api.md). У цьому інкременті немає тредів і архівації каналів.

Документ зберігає мотивацію та домовленості. Після реалізації фактичні гарантії мають бути виражені схемою БД, транзакціями, контрактами API й тестами; текст сам по собі їх не забезпечує.

## Філософія моделі

Чат — це спільний контекст людей, а не тільки список текстів. Повідомлення, зміна каналу й дзвінок можуть бути приводом для відповіді або точкою повернення в історію, але мають різні правила життя. Тому модель відповідає на три окремі запитання:

1. **Що відбулося і як цим керувати?** Предметна сутність зберігає свої дані та інваріанти: `chat_messages` — авторський вміст, `call_sessions` — стан дзвінка, `system_events` — історичний факт події.
2. **Де це стоїть у розмові?** `channel_entries` дає одну стабільну позицію, курсор, permalink і основу для read/unread. Це вузька частина write-моделі, а не копія вмісту та не довільний JSON-лог.
3. **Як людина це бачить?** API складає типізовану read-проекцію, а клієнт додає дату, групування та unread divider. Вигляд може змінюватися без міграції історичних фактів.

Критерій збереження в `channel_entries`: запис має займати стабільне місце, до якого можна повернутися з посилання, відповіді або курсора. Typing, presence, тимчасовий стан камери, divider та локальна чернетка цього критерію не виконують. Edit, pin, reaction і завершення дзвінка змінюють уже наявний запис або його предметну сутність, не займаючи нову позицію. Poll та invite можуть жити в окремих таблицях і відображатися як блоки повідомлення, якщо вони не потребують власної незалежної позиції.

Це свідомий компроміс між гнучкістю та явністю. Новий **вид предметних даних** зазвичай не змінює індекс позицій. Новий **вид самостійного запису історії** змінює його схему, тип проекції та правила unread; таке рішення варто робити явно, бо воно впливає на поведінку всіх клієнтів.

## Межі модулів

`CommunitiesModule` і `SocialModule` — кореневі композиційні модулі для `AppModule`: вони імпортують субмодулі, але самі не реєструють провайдерів, контролерів чи exports. Social залежить від точкових контрактів `channel-access` та `channel-audience`; Communities не залежить від Social. Social володіє позиціями історії та взаємодіями людей у наявному каналі: повідомленнями, reply, quote, mentions, pins, reactions, пересиланням і read-state. HTTP-маршрут `/channels/:channelId/messages` не визначає межу Nest-модуля.

У Communities окремі Nest-модулі `channel-categories`, `channels`, `memberships`, `channel-access` і `channel-audience`. Вузькі модулі репозиторіїв каналів і членства дають `channel-access` доступ до обох контрактів без циклу між feature-модулями. Кожен споживач імпортує потрібний субмодуль безпосередньо.

```text
src/components/social/
  social.module.ts
  entries/          порядок і видача seq; без довільного публічного CRUD
  messages/         send, edit, delete, reply, quote; events/ поряд із повідомленням
  mentions/         похідний індекс згадок та перевірка адресатів
  pins/             закріплення; власні events/ поряд із pin
  read-state/       курсор прочитання
  forwarding/       оркестрація пересилання набору повідомлень
  history/          фасад читання та складання проєкції
  realtime/         спільна функція доставки в авторизовану кімнату
  system-events/    збережені системні записи, коли для них буде окремий use case
```

Кожен реалізований slice має власний Nest-модуль і експортує тільки потрібні іншим slices провайдери. `messages`, `entries`, `pins` і `read-state` мають власні вузькі інваріанти. `forwarding` координує декілька повідомлень і позицій в одній транзакції. `history` читає entries одним обмеженим JOIN-запитом, додаючи read-state окремо; він не викликає write-сервіси заради проєкції. Контракти application events живуть поряд із сутністю, яка їх породжує (`messages/events`, `pins/events`, `forwarding/events`); локальні gateway обробляють події своїх slices. `system-events` означає предметні записи історії, а не загальну шину подій.

На web `features/communities` володіє оболонкою каналу та участю, `features/social` — стрічкою, composer, рендером повідомлень, вибором і діями над ними. Сторінка поєднує ці features. Віддалений стан історії належить query cache Social; вибір повідомлень — локальному стану розмови. Чистий спільний Markdown-контракт може бути окремим workspace-пакетом без Nest, React і БД.

## Рішення

Обираємо окремі предметні таблиці та тонкий **канонічний індекс позицій** `channel_entries`. Це варіант окремих моделей із єдиним порядком історії. `channel_entries` є джерелом істини лише для факту присутності запису і його позиції в каналі. Текст повідомлення, стан дзвінка, реакції, вкладення й системні події мають власні джерела даних. Відповідь API є проекцією цих даних.

Сторінка історії вибирається з `channel_entries` за `seq`; деталі вибраних записів завантажуються пакетно за типом або через обмежену кількість `LEFT JOIN`. SQL `UNION` між усіма предметними таблицями для кожної сторінки не потрібен. Рішення про конкретний спосіб завантаження деталей приймаємо за вимірюваннями: сама модель не гарантує швидшого читання.

## Цільова структура

```text
channels
  id, ..., last_entry_seq bigint NOT NULL DEFAULT 0

channel_entries
  id, workspace_id, channel_id, seq bigint, created_at
  message_id? | system_event_id? | call_id?

chat_messages
  id, workspace_id, channel_id, author_member_id, content_markdown
  reply_to_message_id?, quote_snapshot?, forward_origin?, edited_at?, deleted_at?, client_nonce?

system_events
  id, workspace_id, channel_id, event_type, actor_member_id?, payload

call_sessions
  id, workspace_id, channel_id, started_by_member_id, started_at, ended_at?, status, ...
call_participants
  call_id, member_id, joined_at, left_at?
```

**Ядро історії — три таблиці**: уже наявні `channels`, нові `channel_entries` та `chat_messages`. `system_events` і таблиці дзвінків з'являються разом зі своїми функціями; показані вище `quote_snapshot` і `forward_origin` позначають семантику, а не остаточну форму SQL-колонок. Таблиці доступу (`workspace_members`, `channel_memberships`) вже існують поза ядром; pins, reactions, вкладення та похідний індекс mentions додаються за потреби й не розширюють таблицю позицій.

На першому кроці `channel_entries` посилається на повідомлення. `system_event_id` і `call_id` — майбутні типізовані nullable FK; після їх появи рядок має рівно одне предметне посилання (`CHECK (num_nonnulls(...) = 1)`). Зв'язки перевіряють той самий workspace і channel через складені FK; кожне посилання унікальне, щоб один предметний запис не займав дві позиції. Додатковий тип стабільного запису потребує явної міграції індексу. Poll/invite зазвичай є частиною користувацького повідомлення: їхній стан живе в окремих таблицях, а `blocks` збираються в API-проекції без загального JSON-конструктора у `chat_messages`.

`UNIQUE(channel_id, seq)` дає один порядок і keyset-пагінацію. У цьому інкременті одна лінійна стрічка без тредів. `reply_to_message_id` вказує на повідомлення того самого каналу; quote додає знімок вибраного фрагмента й посилання на оригінал, щоб пізніша зміна джерела не змінювала вже надісланий контекст. Виділення тексту до відправлення — дія інтерфейсу, а не окрема предметна сутність. Pin є окремим зв'язком із повідомленням і не займає позиції.

Персональні `channel_memberships.last_read_entry_seq` та майбутній `manual_unread_from_seq` задають read/unread для єдиної стрічки. Бейдж першого інкременту рахує нові користувацькі повідомлення, крім власних і tombstone; системні записи й дзвінки до нього не входять. Сам факт доставки Socket.IO не рухає курсор. При вступі в канал курсор встановлюється на поточний `last_entry_seq`.

## Вміст і дії над повідомленнями

Канонічний вміст повідомлення в БД та API — Markdown. На записі сервер розбирає ввід у тимчасове AST, перевіряє дозволені конструкції та посилання, нормалізує дерево й серіалізує його в канонічний Markdown. AST не зберігається. Під час цього проходу сервер витягає структуровані mentions зі стабільними `member_id`; самих видимих `@імен` недостатньо. Індекс mentions для сповіщень може зберігатися окремо, але є похідним від Markdown. На клієнті канонічний Markdown знову розбирається й відображається через обмежений registry компонентів. Граматика, версія формату та правило ідемпотентності `parse → normalize → serialize` мають бути спільними для API й web.

Орієнтир взаємодії — одна стрічка в стилі Telegram: reply на конкретне повідомлення, quote вибраного фрагмента, декілька pins, вибір декількох повідомлень і дії над набором. Вибір живе в UI як набір `message_id`; сервер повторно перевіряє кожен елемент. Batch-мутація є атомарною: якщо хоча б один елемент недоступний або дія заборонена, не змінюється жоден. Копіювання у буфер обміну є клієнтською дією; forward створює нові повідомлення й нові entries в цільовому каналі в порядку вибору. Forward зберігає знімок вмісту; посилання на джерело відкривається лише за актуального права читання джерела. Семантика копіювання вкладень визначається разом із приватним media-сховищем.

## Запис і читання

1. Створення повідомлення: після нормалізації вмісту в одній транзакції заблокувати канал, перевірити активне членство та право запису, перевірити nonce, вставити `chat_messages`, збільшити `channels.last_entry_seq`, вставити `channel_entries` з новим `seq` і похідні mentions. Операції вступу, виходу й видалення каналу мають узгоджений порядок блокувань. Унікальність `(channel_id, author_member_id, client_nonce)` робить повтор POST ідемпотентним; повтор із тим самим nonce та іншим вмістом є конфліктом.
2. `GET /channels/:id/messages` є маршрутом історії й повертає типізовані `ConversationItem[]` із `seq` та вкладеною проєкцією. У першому інкременті є лише `MESSAGE`; `SYSTEM_EVENT` і `CALL` додаються разом із відповідними предметними моделями. `POST /channels/:id/messages` створює лише користувацьке повідомлення. Дата, групування авторів та unread divider обчислюються в UI і не зберігаються.
3. Сторінка історії: `WHERE channel_id = ? AND seq < cursor ORDER BY seq DESC LIMIT ?`. Для відновлення після reconnect потрібне читання записів із `seq > cursor`. Перед обома запитами перевіряти актуальне право читання. Клієнт також оновлює видимі записи, бо edit, pin і reaction не отримують нового `seq`.
4. Read-state рухається лише за явним підтвердженням клієнта після показу даних і не може перейти за верхню позицію знімка історії, яку клієнт справді отримав. Нові записи після цього знімка залишаються непрочитаними.

Редагування замінює канонічний Markdown та похідні mentions в одній транзакції. Видалення залишає tombstone, а реакції та вкладення посилаються на `chat_messages.id`. Новий seq для цих дій не видається. Після commit use case публікує типізовану application event, визначену поряд із її предметною сутністю; WebSocket listener поза Social перетворює її на транспортний сигнал. Доставка через локальний emitter є best effort: після reconnect клієнт відновлює історію через REST. Для декількох інстансів потрібен спільний pub/sub, а для гарантованої доставки після commit — outbox; ці механізми не змінюють доменні контракти.

`system_events` — майбутні збережені факти Social, яким потрібна власна позиція. Зміни в Communities не зобов'язані створювати такий запис: Communities залишається незалежним. Якщо пізніше потрібна історична подія про зміну каналу чи дзвінок, окремо визначити контракт інтеграції й гарантію атомарності між відповідними модулями.

## Межі цілісності й перший інкремент

FK з `channel_entries` гарантує, що видимий рядок посилається на наявний предметний запис. Він сам по собі не забороняє предметний запис без позиції. Усі створення виконуються одним транзакційним шляхом, без окремого публічного API для предметних рядків; інтеграційний тест перевіряє відсутність осиротілих записів. Якщо з'являться незалежні writers, посилити цю умову перевіркою в БД.

Перший інкремент: зафіксувати обмежену граматику канонічного Markdown; додати `last_entry_seq`, `channel_entries` та вузькі `chat_messages`; реалізувати транзакційне надсилання, курсорну історію, базовий read-state і відображення у web. Наступні slices додають reply/quote, pins, forwarding з batch-діями та похідні mentions без зміни принципу позицій. `system_event_id` та `call_id` додаються разом зі своїми предметними таблицями; правило «рівно одне посилання» розширюється тоді ж. Перевірити конкурентні POST, retry з nonce, доступ до приватного каналу, вихід учасника під час POST, збереження позиції після edit/delete та read race зі snapshot. Поточне видалення каналу залишається фізичним; воно прибирає його історію та permalinks, тому політику FK і каскадів потрібно зафіксувати до міграції.

**Переваги обраного підходу:** один індекс для сторінок і переходу до повідомлення; однакова адресація історії каналів і DM; стабільні посилання попри edit/delete; незалежні правила повідомлень, системних подій і дзвінків; типізовані FK замість неперевіреного `source_type/source_id`; read-проекцію можна змінювати для web/mobile без зміни доменних фактів. Це також залишає блоки poll/invite поза базовою таблицею повідомлень.

**Ціна й межі:** створення одного елемента означає два записи в одній транзакції; читання сторінки потребує завантаження деталей; новий самостійний тип вимагає міграції `channel_entries`; FK з індексу не гарантує, що кожен предметний рядок має позицію; `channels.last_entry_seq` серіалізує одночасні записи в одному каналі. Для очікуваних невеликих команд це прийнятна початкова ціна, але не твердження про швидкість без вимірювань. Якщо з'явиться гарячий канал або багато типів записів, вимірюємо затримку транзакцій, план запиту сторінки та кількість запитів на hydration перед оптимізацією.

Ці альтернативи є орієнтирами, а не рецептами копіювання. [Zulip Message/SubMessage](https://github.com/zulip/zulip/blob/main/zerver/models/messages.py) показує ще один варіант: базове повідомлення та пов'язані підзаписи для додаткової поведінки. Наш вибір виходить із локальних вимог до приватного доступу, майбутніх типів історії та одного монотонного порядку в межах каналу.

## Підстава для вибору

- [Slack message events](https://docs.slack.dev/reference/events/message/), [Slack history/threads](https://docs.slack.dev/messaging/retrieving-messages/) і [Discord Message Object](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx) показують типізовані записи спільної історії; їхні публічні контракти не розкривають фізичну схему БД.
- [Matrix specification](https://spec.matrix.org/latest/) відділяє тип події від її місця в room timeline.
- [PostgreSQL constraints](https://www.postgresql.org/docs/16/ddl-constraints.html) дозволяють `CHECK`, `UNIQUE` та складені FK для цілісності типізованих посилань; [обмеження успадкування](https://www.postgresql.org/docs/17/ddl-inherit.html) також показують, що `UNIQUE` не поширюється автоматично між окремими таблицями.
