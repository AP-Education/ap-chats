# Асинхронний UI

## Межі стану

- Route, якому обов’язково потрібен робочий простір, розміщується під `RequiredWorkspaceLayout`. Gate один раз вирішує перше завантаження, помилку й відсутність простору. Дочірній route отримує гарантований простір через `useRequiredWorkspace`.
- Компонент, який показує дані, сам викликає свій query hook. Сторінка не передає вниз `UseQueryResult` або набір прапорців завантаження.
- Query key містить стабільний `identity`, а не access token. Token використовується тільки для запиту. Ключ також містить workspace ID, щоб дані різних просторів не змішувалися.

## Стани читання

| Ситуація                    | UI                                                               |
| --------------------------- | ---------------------------------------------------------------- |
| Перший запит без даних      | Одразу показати каркас того самого розміру й форми, що й вміст.  |
| Повторний запит із даними   | Залишити дані та керування на місці. Не перекривати їх спінером. |
| Помилка без даних           | Показати помилку з дією повторного запиту.                       |
| Помилка з кешованими даними | Залишити дані, окрім відповіді про втрату доступу до ресурсу.    |
| Успішний порожній результат | Показати empty state тільки після відповіді сервера.             |

Для переходу зі списку до каналу detail query бере початкові дані з кешу списку того самого користувача й простору. Незнайомий канал отримує власний каркас. Не підставляти дані попереднього workspace як `placeholderData`.

Під час переходу між каналами зберігати розміри заголовка, бокової панелі й поля вводу. Composer зберігає окрему чернетку для кожного каналу та змінює її до показу наступного кадру. Розмір екрана читається синхронно через media query, щоб після монтування не мінявся режим layout.

## Мутації

- Коли ID і наслідок відомі, скасувати поточний refetch, оновити відповідні list/detail записи в кеші, зберегти попередні значення для відкату, а після відповіді записати серверний результат і узгодити запити через invalidation.
- Для створення, де ID призначає сервер, показувати pending стан дії та вставляти отриманий запис у кеш одразу після відповіді. Навігація може використовувати справжній ID без тимчасових маршрутів.
- Видалення категорії разом із самою категорією переносить її канали в «Без категорії» у кеші. Відкат повертає обидві частини.
- Видалення каналу прибирає його зі списків одразу після підтвердження. Відкритий канал одразу переходить до списку каналів; API фізично видаляє запис і каскадно видаляє його учасників. Помилка повертає канал у кеш.
- Помилка мутації має повернути попередній стан і бути видимою користувачу там, де дію було виконано.

Не додавати штучну затримку перед каркасом або мінімальний час показу спінера: швидкий запит просто не встигне помітно показати каркас, а повільний залишить стабільну геометрію. Для нових сценаріїв спершу визначити власника запиту та межу каркаса, а потім додавати оптимістичну зміну лише там, де її наслідок однозначний.
